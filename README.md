# Breax Invoicing

PHP 8.2+ and MySQL/MariaDB invoicing application. The web root (`index.php`) routes signed-out visitors to login and signed-in users to the dashboard.

## Renewal reminder scheduler

After importing the schema, apply the idempotent reminder migration with the CLI:

```text
php database/migrate_renewal_reminder_log.php
```

Configure `RENEWAL_REMINDER_TIMEZONE=Africa/Nairobi`, `RENEWAL_REMINDER_HOUR=8`, `RENEWAL_REMINDER_STAGES=30,7`, and `RENEWAL_REMINDER_EXPIRED_DAYS=90` in `.env`. Recipients are managed under **Company settings → Renewal reminders**; if unset, the first administrator account email is used. SMTP credentials and sender details come from the existing `MAIL_*` settings. Set `APP_BASE_URL` to the public site URL because the job runs without a browser request.

For Linux cron, schedule the PHP CLI every day at 08:00 East Africa Time:

```cron
CRON_TZ=Africa/Nairobi
0 8 * * * /usr/bin/php /path/to/breax-invoicing-system/system/send_renewal_reminders.php >> /path/to/breax-invoicing-system/logs/renewals-cron.log 2>&1
```

For Windows Task Scheduler:

1. Open **Task Scheduler** and choose **Create Basic Task**. Name it `Breax renewal reminders`.
2. Select **Daily** and set the start time to **08:00**. Set Windows' time zone to **(UTC+03:00) Nairobi** so the trigger matches `Africa/Nairobi`.
3. Choose **Start a program**. Set **Program/script** to `C:\wamp64\bin\php\php8.2.29\php.exe`, **Add arguments** to `C:\wamp64\www\breax-invoicing-system\system\send_renewal_reminders.php`, and **Start in** to `C:\wamp64\www\breax-invoicing-system`.
4. Finish the wizard and check **Open the Properties dialog**. On **General**, select **Run whether user is logged on or not** if the scheduled Windows account can read the project and `.env` and write to `logs`.

The equivalent command is:

```text
"C:\wamp64\bin\php\php8.2.29\php.exe" "C:\wamp64\www\breax-invoicing-system\system\send_renewal_reminders.php"
```

The job writes its own protected log to `logs\renewals.log`; if your WAMP installation uses another PHP version, select that version's `php.exe`.

Run `php system/send_renewal_reminders.php --dry-run` to preview recipients and items without sending or recording reminders. `--today=YYYY-MM-DD` simulates a date, `--send-test` sends a clearly marked fake digest to configured recipients, and `--force` resends all qualifying real items regardless of the reminder log. Never schedule `--force`. To roll back the reminder log table, run `php database/migrate_renewal_reminder_log.php --down`; the additive email-log type and expanded CC column are retained to preserve mail history.

## Install

1. Create a MySQL/MariaDB database and a dedicated application user with privileges limited to that database. Import `database/schema.sql` into the selected database; the schema deliberately does not create or select a database, so it works with cPanel's account-prefixed database names. It seeds the three hosting packages and does not delete or replace records. For an existing installation, back up the database and run only the migrations not already applied, in the order listed in the existing-installation section below.
2. Configure these environment variables for the PHP/Apache process:
   - `APP_DB_HOST` (defaults to `127.0.0.1`)
   - `APP_DB_NAME` (defaults to `breax_invoicing`)
   - `APP_DB_USER`
   - `APP_DB_PASSWORD`
   - Optional `APP_CURRENCY` (defaults to `KES`)
   - Optional `FX_STALE_AFTER_HOURS` (defaults to `3`; controls when Dashboard and Reports mark cached exchange rates as potentially out of date)
   - `APP_BASE_URL` (public application URL including any subdirectory, for example `https://invoicing.example.com`; used for public invoice links and emails)
   
   For local WAMP, configure `.env`. In production, prefer placing the secrets file outside the web document root and set `APP_ENV_FILE` to its absolute path in both the web PHP environment and scheduled CLI environment. If the host requires `.env` inside the project, the root `.htaccess` denies web access to it; still use restrictive file permissions and never put secrets in source control. Set `APP_ENV=production`, the cPanel-prefixed database name/user, the actual database host, and `APP_BASE_URL` to the final HTTPS URL. Do not rely on local defaults or the example values. Quote `.env` values containing `;`, `#`, or `=`.
3. Use PHP 8.2+ with `pdo_mysql`, `mbstring`, `openssl`, and `fileinfo` enabled. Run `composer install --no-dev --optimize-autoloader` and `npm ci --omit=dev`. Invoice email PDFs also require Node.js, `playwright-core`, `qrcode-generator`, a runnable headless Chromium/Chrome binary, PHP `proc_open`, and writable temporary storage; cPanel shared hosting may not provide these, so verify them before enabling invoice email. Set `INVOICE_PDF_NODE` and `INVOICE_PDF_BROWSER` to the server's executable paths when they are not on the default search path. Set the document root to the project directory where possible, enable the required Apache `.htaccess` overrides, and ensure `assets/uploads` is writable by PHP. Do not upload `.idea`, local `.env`, `node_modules`, or development documents. Preserve `assets/uploads` and its `.htaccess`; transfer existing logo files when restoring a database that refers to them.
4. Sign in, update Company Settings, and set prices for the seeded hosting packages before using them on invoices. Enter the structured M-Pesa and bank email payment fields there; email sending refuses to proceed until those fields and the other required template values are present.
5. Configure SMTP as described below. Apply the email, alert, and payment-receipt migrations before using those features. Invoice emails are generated and sent directly during the request. Internal overdue alerts are checked after an opted-in admin opens a page after the configured time; overdue reminders remain manual.

### cPanel deployment and upgrade

- Select PHP 8.2 or newer in **MultiPHP Manager** for the production domain and enable **Force HTTPS**. Confirm the host permits `.htaccess` overrides and `proc_open`; the app's extensionless URLs, access protections, and PDF attachments rely on these Apache/PHP capabilities. Prefer a dedicated HTTPS subdomain/document root for the app.
- Create the database and database user in cPanel. Import the current schema into the selected database for a new installation. To move existing data, export/import the existing database instead of importing the fresh-install schema over it; preserve the `assets/uploads` files referenced by Company Settings. Configure the app's database name, username, password, and host explicitly.
- Keep production secrets outside the public document root when possible. If stored outside the project, set `APP_ENV_FILE` to its absolute path in the site's `.htaccess` (for example, `SetEnv APP_ENV_FILE /home/CPANEL_USER/breax-invoicing.env`) and the cron command (for CLI jobs). If cPanel cannot pass environment variables to PHP, use a protected `.env` in the project root; test that requesting `/.env` returns 403/404 before launch.
- Build dependencies from the project root with Composer and npm as above, or upload their production-only installed directories. Run `php system/check_production.php` using the same PHP version and environment as production. Resolve every `FAIL` before launch. This non-web CLI check does not send email; it checks PHP capabilities, configuration shape, database schema, upload/temp permissions, and PDF runtime availability.
- For a fresh database, import `database/schema.sql` and create the first administrator from the login page. For an existing database, make a backup, then run any still-needed migrations in this order: `migrate_public_invoice_links.php`, `migrate_remove_product_renewal_price.php`, `migrate_remove_product_price.php`, `migrate_invoice_currencies.php`, `migrate_email.php`, `migrate_invoice_email_permissions.php`, `migrate_admin_overdue_alerts.php`, `migrate_payment_reference_unique.php`, `migrate_payment_received_emails.php`, `migrate_remove_product_description.php`, `migrate_dashboard_currency_conversion.php`, `migrate_remove_customer_tax_id.php`, `migrate_customer_domains.php`, `migrate_customer_google_workspaces.php`, `migrate_admin_overdue_invoice_reports.php`, `migrate_domain_expiry_reports.php`, and `migrate_admin_google_workspace_reports.php`. Run each only if it has not already been applied; use the cPanel PHP CLI binary and the production environment. Some migrations alter columns or indexes, so take and verify a backup first.
- Configure cPanel Cron Jobs for report delivery on day 1 at 09:00 Africa/Nairobi, converting the hour if the host's cron scheduler uses a different timezone. Use a command like `cd /home/CPANEL_USER/public_html && APP_ENV_FILE=/home/CPANEL_USER/breax-invoicing.env /usr/local/bin/ea-php82 system/admin_overdue_reports.php --send >> /home/CPANEL_USER/logs/admin-overdue-reports.log 2>&1`, replacing the account path, PHP CLI binary, and log path with those shown by the host. Set the same `APP_ENV_FILE` path in `.htaccess` for web requests. If the `.env` is in the project root, omit `APP_ENV_FILE` from both places. Run `php system/admin_overdue_reports.php --preview` first; it generates all three PDFs without sending email. The report runner logs each report result and exits nonzero when a report fails.
- Configure a separate cPanel Cron Job to refresh exchange rates every three hours (minute `0`, hour `*/3`, every day). Use `cd /home/CPANEL_USER/public_html && APP_ENV_FILE=/home/CPANEL_USER/breax-invoicing.env /usr/local/bin/ea-php82 system/refresh_exchange_rates.php >> /home/CPANEL_USER/logs/exchange-rates.log 2>&1`, replacing the paths and PHP CLI binary with the host's values. If `.env` is in the project root, omit `APP_ENV_FILE`. The Dashboard and Reports also refresh rates when opened if the last successful refresh was at least three hours ago; the scheduled job keeps rates checked even when nobody is signed in. A failed or overdue refresh exits nonzero and is written to the log. On local Windows/WAMP, create a Task Scheduler task that runs `php.exe` with `system\refresh_exchange_rates.php` every three hours.
- If moving from a previous Windows report task, disable it after the cPanel cron is verified and cutover is complete, to avoid sending from both installations.

For a local WAMP database that still uses MySQL's default `root` account, set `APP_DB_USER=root`; configure its password with `APP_DB_PASSWORD` rather than editing application code.

## Included workflows

- Session-based login/logout, one-time first-user setup, CSRF tokens, prepared SQL statements, escaped output, and protected dashboard routes.
- Customer and product/service creation, editing, search, and archive actions.
- Draft invoice creation/editing, issue workflow, immutable issued line snapshots, quantity/discount/tax calculations in integer cents, invoice print layout, and partial/full manual payments. Company settings control which of KES, USD, GBP, and EUR are available for invoices. Invoice amounts, payments, PDFs, and invoice emails remain in the saved invoice currency; dashboard and Reports aggregates alone convert to KES using a daily exchange-rate snapshot saved when each invoice is issued. The dashboard/reporting conversion never changes invoice, payment, PDF, or email amounts. Rates are fetched from the daily historical KES-base currency feed hosted by jsDelivr; exact issue-date rates are used when available, and the latest cached rate is used and retained if a historical quote cannot be retrieved. Invoice Terms/Notes use the entered invoice note, or the Company Settings Payment Terms when left blank. The invoice form can add already-received payment records before saving; new invoices/items and their payments are committed together, and existing draft payments can be removed before saving.
- Dashboard and Reports share an Exchange rates panel sourced from the existing daily rate cache. The panel displays rates in KES per foreign currency unit and marks them potentially out of date after `FX_STALE_AFTER_HOURS` (3 hours by default); each successful check refreshes its timestamp even when the rate values have not changed. Older cache rows without refresh timestamps use midnight on their rate date as an estimate.
- Random, revocable public invoice links with a read-only invoice page, live payment status, noindex/no-referrer headers, and per-IP request throttling. Staff manage links from **Public invoice links**; the QR code is shown on invoice pages whenever an active public link exists.
- Database-driven dashboard, payment history, company settings, profile, and basic revenue/customer reports.

## Operational notes and limitations

- Run `database/schema.sql` manually for initial installation; the app intentionally does not run schema changes against an existing database automatically.
- Rerun `php database\migrate_dashboard_currency_conversion.php` after deploying the exchange-rates panel so existing installations add the rate refresh timestamp; the migration is idempotent.
- Public invoice URLs contain bearer tokens. `.htaccess` marks these requests as `no_log_public_invoice`; configure the Apache virtual-host `CustomLog` directive with `env=!no_log_public_invoice` so access logs do not record token paths. The PHP application does not log token values.
- Invoice emails are sent synchronously after the invoice transaction commits. The request renders the current PDF, makes one SMTP send attempt, and records `sent` only after SMTP accepts the message. Delivery failures are recorded as `failed`, and permanent recipient rejections as `bounced`. Staff can explicitly send a failed invoice-issued email again from its invoice log; no background delivery or automatic retries are used.
- The invoice page's **Print / Save PDF** action deliberately remains the browser's native print dialog. Email attachments use `generateInvoicePdf()` in `includes/email.php`, which renders the same `includes/invoice_document.php` and `assets/css/styles.css` in headless Edge/Chrome through Playwright, using a 1200px viewport, print media, A4, exact print colors, and a server-generated QR. Each direct render uses and removes its own temporary browser profile. Logos are embedded as data URIs for the server render. Install the Node dependencies (`playwright-core` and `qrcode-generator`) with `npm install`; configure `INVOICE_PDF_NODE` or `INVOICE_PDF_BROWSER` only if the server does not find the default executables.
- The issued-invoice email is sent once when an invoice is issued. Recording a payment on an issued invoice automatically sends a customer receipt with the invoice total, amount paid to date, outstanding balance, transaction history, public invoice link, and updated PDF. A payment that settles the invoice uses the paid-in-full template. Payments staged while an invoice is a draft are included in a receipt when that invoice is issued. Payment receipts are sent after the payment transaction commits; delivery failures do not undo the payment and are recorded in the email log.
- The overdue email uses `emails/email-invoice-overdue.html` and is sent only by a staff action on an overdue invoice. It shows the remaining balance and whole days overdue in the Africa/Nairobi time zone; there is no automatic overdue reminder.
- Staff accounts are administrator accounts. The `can_send_invoice_emails` permission gates the invoice reminder toolbar and its POST handler; the permission migration grants it to existing administrators, and the first administrator created during setup receives it.
- New payment records require a transaction reference unique within that invoice. Existing installations must run `php database\migrate_payment_reference_unique.php`; the migration reports invoice IDs with duplicate references without changing payment records, which must be resolved before rerunning it.
- The overdue reminder's server-side checks require an unpaid invoice with an active public link and a due date before today in Africa/Nairobi. Becoming overdue, opening the invoice, or recording a payment does not send a reminder.
- Internal overdue alerts use `emails/email-admin-overdue-alert.html`. Admins explicitly opt in from **My profile**; the preference defaults off, including for the account creator. Alerts go separately to opted-in admin account addresses, never to the client, and link to the private staff invoice page. Each alert gets one send attempt; failed alerts are logged and are not automatically retried. `MAIL_CC` is deliberately not copied on these alerts. `MAIL_MODE=log` records an alert as not sent; `sandbox` requires `MAIL_TEST_ADDRESS` and redirects these internal alerts there; `live` sends to the opted-in admin.
- Run `php database\migrate_admin_overdue_alerts.php` once. It records the first-deployment date and marks invoices already overdue on that date as suppressed without sending; its console output reports the suppressed count. Do not rerun or remove the alert baseline/configuration tables to repeat initialization.
- Configure `ADMIN_OVERDUE_ALERT_TIME` (default `09:00`), `ADMIN_OVERDUE_REPEAT_DAYS` (default `0`, off), and `ADMIN_OVERDUE_MAX_ALERTS` (default `3`) in `.env`. After 09:00 Africa/Nairobi, the first opted-in email-capable admin page visit starts the check in a non-blocking same-origin request. An atomic database timestamp claim and lock prevent concurrent duplicate runs. Each run is limited to 20 alerts and 30 seconds; when a batch stops at a limit, remaining invoices are considered on the next admin visit. The **Run overdue check now** button on Email delivery and the optional `POST /system/overdue-check.php` endpoint run the same check manually. Configure a long random `OVERDUE_CHECK_TOKEN` and send it as `Authorization: Bearer <token>` to use the endpoint; no scheduler or token is required for normal operation. With no outside scheduler, alerts run only when an admin visits after the configured time (or the secured endpoint is called); they are not sent at an exact scheduled time.
- Client email is sent directly through SMTP regardless of `MAIL_MODE`; internal admin overdue alerts honor `MAIL_MODE` as described above. Set `APP_ENV=production`; other environments are blocked from sending. Sample templates are sent to the test recipient entered by staff.
- **Gmail setup:** In the Google Account Security settings, turn on **2-Step Verification**, then create an **App password** (choose Mail or Other and name it for this application). Put the full Gmail address in `MAIL_USERNAME`, the app password (without display spaces) in `MAIL_PASSWORD`, and normally the same address in `MAIL_FROM_ADDRESS`. Set `MAIL_FROM_NAME` to the company display name (blank uses Company Settings), `MAIL_REPLY_TO` if needed, and `MAIL_CC` for an optional internal copy. Fill `SUPPORT_EMAIL`, the public `APP_BASE_URL`, and a full HTTPS `LOGO_URL`. Do not use the normal Gmail password. An app password requires 2-Step Verification; Google may not offer one for some account/security configurations.
- Gmail only sends from the authenticated account or a verified **Send mail as** alias. If using an alias, add and verify it in Gmail settings first, then use it for `MAIL_FROM_ADDRESS`. Gmail limits each message, including attachments and MIME encoding, to 25 MB.
- **Personal Gmail DNS:** Sending as the Gmail address itself needs no DNS changes. For Google Workspace on your own domain, first add/merge one SPF TXT record at `@` with `v=spf1 include:_spf.google.com ~all` (do not publish multiple SPF records). In Admin Console, go to **Apps → Google Workspace → Gmail → Authenticate email**, generate a 2048-bit DKIM key, publish the displayed TXT host (usually `google._domainkey`) and exact generated value, then start authentication. Publish a DMARC TXT record at `_dmarc`, initially `v=DMARC1; p=none; rua=mailto:postmaster@yourdomain.example`, replacing the report mailbox with one you monitor; tighten policy after reviewing reports and confirming SPF/DKIM alignment. Workspace provides the account-specific DKIM TXT value.
- To change SMTP provider, edit only `MAIL_HOST`, `MAIL_PORT`, `MAIL_ENCRYPTION`, `MAIL_USERNAME`, `MAIL_PASSWORD`, and `MAIL_FROM_ADDRESS` in `.env`; provider examples are in `.env.example`. Keep the selected provider's SPF/DKIM records and a DMARC policy published for your sending domain. SPF and DKIM values are provider/domain-specific; once you choose another provider, use its exact DNS values rather than copying Google's. From addresses may need to be verified with that service.
- The staff-only **Email delivery** page can test the SMTP connection without sending and send sample invoice templates directly with a synthetic invoice PDF. The partial-payment sample includes two payments so the PDF demonstrates the transaction table. Direct delivery is capped by `MAIL_MAX_PER_DAY`; messages are not deferred when the daily cap is reached.
- Overdue invoice, domain renewal, and Google Workspace renewal reports cover all records matching the dashboard's overdue criteria as of the generation date. The same shared query supplies dashboard counts and report records. Reports go only to administrator accounts opted in to internal alerts; the day-1 schedule, live-mode, locking, and duplicate protections are unchanged. Run `php system/admin_overdue_reports.php --preview` from the project root to generate all three PDFs and inspect their counts without sending. Check the PHP error log or configured cron log for per-report results.
- The removed Service Renewals screen does not delete existing `customer_services` tables or records; fresh installations no longer create that table.
- Run `php database\migrate_email.php` after deploying direct email delivery. The migration removes queue and attempt-count columns and restricts statuses to `sent`, `failed`, or `bounced`. It prints and pauses on any legacy statuses it cannot safely classify; review those rows before deciding how to handle them. No background email worker or email queue task is required.
- Run `php database\migrate_payment_received_emails.php` once to allow automatic payment-receipt emails in the email log.
- Company logos can be uploaded from Company Settings as PNG, JPEG, or WebP images up to 2 MB; ensure PHP can write to `assets/uploads`.
- Payment gateways, refunds, automatic invoice generation, user administration, and audit-log screens are not implemented.
- Monetary values are stored in MySQL `DECIMAL` columns and invoice calculations are derived server-side. Manual payment records are transactionally checked against the outstanding balance.
